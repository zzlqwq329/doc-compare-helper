输入同一份制度的两个 Markdown 版本，识别未变、修改、删除、新增和跨章移动。对无法唯一配对的候选标记为待核对。对比结果保留版本、段落编号、章节、行号和原文，方便逐条复核。

## 运行示例

在仓库根目录运行以下命令。文档解析和对比只使用 Python 标准库，已在 Python 3.14 下验证。

```sh
python project/reader.py
python project/compare.py
```

打开 `outputs/comparison.json` 查看结果。例如，报销期限由「10个工作日」改为「5个工作日」，可分别回到[旧版第 11 行](samples/expense-v1.md#L11)和[新版第 13 行](samples/expense-v2.md#L13)核对。

在 Python 虚拟环境中安装 pytest 后运行 Task 3 的测试。

```sh
python -m pytest project/test_compare.py project/test_guard.py project/test_units.py -q
```

## 怎么一起推进

已确认学习起点：Java 学到面向对象，Python 有语法基础，MySQL 会增删改查；每天可投入 1—2 小时。

采用结对学习。**项目推进对话**负责维护路线、拆分并发布 Task、核对验收结果。**Task 对话**负责代码实现、逐步讲解、运行和排错。代码可以请 AI 起草，你负责理解关键逻辑、实际运行，并亲手修改一处验证理解。

每轮只推进一个能验收的小功能，依次完成这四步。

1. **复用检查。** 先读仓库中相关的代码，再检查项目环境里已经能用的库。列出具体文件或函数、复用理由、确实需要新增的逻辑。没读到的代码标为「待检查」。
2. **白话流程。** 用现有样本说明数据从哪里来、每步做什么、预期得到什么。第一次遇到的功能可以由助手先提一个简单方案。
3. **最小实现。** 任务文档给出这一轮的实现范围和验收条件。在 Task 对话里完成代码并运行核对。
4. **自己动手。** 先预测结果，再亲手改一个小条件或补一个测试，运行验证。

代码是否完成，以运行结果和能否解释为准。进度记录只勾选已经验证的项目。

## 样本约定

`samples/expense-v1.md` 和 `samples/expense-v2.md` 是教学用虚构数据。

1. UTF-8；标题行以 `# ` 或 `## ` 开始；每个非空正文行就是一个段落。这里只支持这份受限格式，不代表完整 Markdown 解析。
2. 文档标题和章节标题不计入正文段落数。V1 有 13 段，V2 有 14 段。
3. 段落编号为 `V1-P001`、`V2-P001` 等，表示“某个固定版本内的定位”，不能凭相同序号认定两段对应。相同文件重复读取应得到相同编号；新版本重新编号。
4. 行号从 1 开始，包含标题和空行。`raw_text` 保留正文原文，仅去掉换行符；比较用的清洗文本以后另存。
5. 固定样本包含 6 处修改、2 处新增、1 处删除、1 处跨章节移动，共 10 处变化。其余 5 对正文未变。
6. 移动指原文未变但所属章节改变；本批暂不包含同章重排或同时移动并修改。章节标题本身不生成变化条目。
7. 新增、删除不能只凭相同序号判定。本批新增与删除是独立条款，不应因为恰好占据相近位置就合成一次修改。

核对答案在 `fixtures/expected-changes.json`，用于后续评估。分析程序只能读取两份原文，不能把答案文件作为识别变化的输入。
