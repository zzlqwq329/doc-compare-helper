# 第三项练习：补齐修改、新增和删除

## 第一小步：给未匹配的段落打分

打开 `project/compare.py`，从 Task 2 留下的 `unmatched_v1` 和 `unmatched_v2` 继续。先对同章内的旧段落和新段落计算正文相似度，打印两个段落编号和分数。今天可以先用 45—60 分钟跑通这一小步，再按验收清单继续。

在项目根目录用 PowerShell 运行。

```powershell
Set-Location -LiteralPath 'D:\Java\文档分析项目'
python .\project\compare.py
```

用 Python 标准库的 `difflib.SequenceMatcher` 计算 `raw_text` 的相似度。分数范围是 0 到 1，越高说明文字越相似。先观察 `V1-P003 → V2-P004` 的报销期限变化，分数应约为 0.93。初审人变化 `V1-P006 → V2-P007` 的分数约为 0.64。

## 为什么先打分

两段内容可能只改了一个金额，也可能恰好有几个相同的词。先看到候选和分数，再决定怎样配对。当前练习用同章候选和文本相似度建立一条可以复查的规则。

## 后续交付：分类并保存结果

1. 沿用 Task 2 的「未变」和「移动」配对。若有正文在两版都出现、且任一版有多条相同正文的情况，把这些未配对记录留为「待核对」。
2. 对其余未配对记录，在同章内找正文不同且相似度达到 `0.60` 的候选。两边都把对方选为唯一最高分时，才能配成一处「修改」。用原始分数比较，打印时可以四舍五入。阈值是这份样本的起点。
3. 对还剩下的段落，有达到阈值的候选但因并列或竞争未配上的，记为「待核对」。旧版没有达到阈值的候选，记为「删除」。新版没有达到阈值的候选，记为「新增」。这一步沿用最初计算的候选，避免先配走一段后把原本有歧义的另一段直接判成新增或删除。
4. 输出各类数量，并保存 UTF-8 文件 `outputs/comparison.json`，供下一项生成报告使用。

## 输入与输出约定

输入还是 `outputs/blocks-v1.json` 和 `outputs/blocks-v2.json`。输出 JSON 用 `items` 列表记录每个结果，每项有 `type`、`old` 和 `new` 三个字段。

| `type` | `old` 和 `new` 怎么填 |
| --- | --- |
| `unchanged`、`moved`、`modified` | 保存两端的完整段落记录 |
| `deleted` | 保存旧版段落，`new` 为 `null` |
| `added` | 保存新版段落，`old` 为 `null` |
| `needs_review` | 每个待核对段落一条记录，保留所属版本的段落，另一端为 `null` |

完整段落沿用 Task 1 的字段，包括 `version_id`、`block_id`、`section`、行号和 `raw_text`。已配对和未配对的段落都应能在输出里找到，且每个输入段落只出现一次。

[人工标注答案](../fixtures/expected-changes.json)只用于运行后的核对。核对时比较变化类型和两端段落编号。

## 卡住时的提示

- 先打印一条旧段落的几个候选，再检查反向视角。一条新段落也可能被多个旧段落选中。
- 验收样本只覆盖基础情况。跨章节且同时改写、拆段或合段，需要以后补新的样本和规则。
- 可以请 AI 起草。自己把阈值暂时改为 `0.70`，先预测哪对修改会漏掉，再运行核对。完成实验后恢复为 `0.60`。
