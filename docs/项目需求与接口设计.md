# 文档对比与证据报告助手 · 需求与接口设计

**状态**　设计草案。项目当前处于本地文档读取与分段练习阶段。下文的 HTTP 接口是 Java Web 版的设计约定。

## 1. 项目需求

制度维护人员需要比较同一份制度的两个版本，找出新增、删除、修改和跨章节移动的条款，并将结果整理成一份可下载、可核查的报告。

用户先创建文档并上传两个版本，选定旧版和新版后提交对比任务。任务完成后，用户查看变化清单，按报告中的章节、行号或页码核对原文，再下载 Markdown 报告。遇到失败时，页面说明原因，并在允许的情况下提供重试入口。

| 编号 | 需求                   | 验收标准                                                                                                     |
| ---- | ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| R1   | 管理同一文档的多个版本 | 上传新版本后，旧版文件和已有报告引用保持有效。任务固定两个版本编号，重试也使用原来的版本                     |
| R2   | 比较正文条款           | 固定样本应识别出 6 处修改、2 处新增、1 处删除和 1 处移动。每个正文段落都有处理记录，无法可靠匹配时标记待核对 |
| R3   | 提供原文证据           | 修改和移动引用两版原文，新增引用新版，删除引用旧版。所有引用都能在本次任务选定的版本中核对，模型推断单独展示 |
| R4   | 管理异步任务           | 提交后立即返回任务编号。用户可以查询进度和失败原因。临时故障可有限重试，同一任务最多发布一份有效报告         |
| R5   | 隔离用户数据           | 服务端对文档、版本、任务、报告和下载检查归属。账号 A 即使拿到账号 B 的资源编号，也无法访问相关内容           |

本地版先支持项目现有的 UTF-8 Markdown 样本格式。文本型 PDF、OCR、复杂表格、组织共享和跨文档研究随阶段扩展。当前样本说明和人工答案见 [项目 README](../README.md) 和 [预期变化清单](../fixtures/expected-changes.json)。

## 2. 功能清单

| 阶段         | 功能                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------- |
| 本地对比     | 读取并分段，记录章节与行号，匹配条款，识别变化，生成带引用的 Markdown 报告                |
| 证据报告     | 增加文本型 PDF 解析。模型解释已识别的差异，程序验证证据编号、版本范围和原文摘录           |
| Java Web     | 登录、文档与版本管理、提交对比、查询任务、查看报告、下载报告。联调用两个预置账号验收权限  |
| 可靠任务     | Python Worker 领取任务，回报阶段，提交结果。Java 管理任务状态、超时恢复、重试、幂等和审计 |
| 检索与 Agent | 在两版授权资料内检索并辅助匹配，提供只读工具，校验工具参数并限制调用次数与耗时            |

## 3. 技术栈与职责

| 层       | 技术选择                                     | 职责                                                                                 |
| -------- | -------------------------------------------- | ------------------------------------------------------------------------------------ |
| 本地分析 | Python 3.11、标准库                          | 读取、分段、比较和报告渲染。先沿用已确认可用的本地环境                               |
| Web 后端 | Java 21、Spring Boot、Spring Security、Maven | 用户登录、资源授权、HTTP 接口、任务调度、报告发布                                    |
| 数据库   | MySQL、Spring JDBC                           | 保存用户、文档、版本、任务、执行记录和报告元数据                                     |
| 文件存储 | 本地文件目录，后续可换对象存储               | 保存不可覆盖的原件、解析结果和报告。服务端分配存储键                                 |
| AI 执行  | Python 独立 Worker、模型 API                 | 解析、匹配、差异解释、证据校验。通过 Java 内部 HTTP 接口领取任务、回报进度和提交结果 |
| 联调     | Apifox，后续增加简单网页                     | 验证请求、响应、错误及完整用户流程                                                   |

浏览器和 Apifox 统一访问 Java。Java 通过 MySQL 保存任务状态，Python Worker 按任务授权取得文件并处理。对比、校验和导出使用同一份结构化结果。检索用于辅助匹配和找依据，正文覆盖仍由对比流程逐段记录。

## 4. HTTP 接口设计

以下 **8 个对外接口**是上传到下载的第一批接口。统一前缀为 `/api/v1`，请求和响应示例中的编号是字符串。登录以外的接口都带 `Authorization: Bearer <accessToken>`。JSON 使用 UTF-8。示例使用本地虚构报销制度。

| 方法与路径                                | 传什么                                                                   | 成功返回                                                    |
| ----------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------- |
| `POST /auth/login`                      | JSON，`username`、`password`                                         | 200，`accessToken`、`expiresIn`                         |
| `POST /documents`                       | JSON，`title`                                                          | 201，`documentId`、`title`                              |
| `POST /documents/{documentId}/versions` | 表单，`file`、`label`                                                | 201，`versionId`、`documentId`、`label`、`fileName` |
| `POST /comparisons`                     | JSON，`baseVersionId`、`targetVersionId`；请求头 `Idempotency-Key` | 202，`taskId`、`status`、`statusUrl`                  |
| `GET /comparisons/{taskId}`             | 路径中的任务编号                                                         | 200，任务状态、阶段、报告编号及错误信息                     |
| `POST /comparisons/{taskId}/retry`      | 路径中的任务编号，无请求体                                               | 202，原 `taskId` 和 `QUEUED` 状态                       |
| `GET /reports/{reportId}`               | 路径中的报告编号                                                         | 200，版本编号、变化条目及原文引用                           |
| `GET /reports/{reportId}/download`      | 路径中的报告编号                                                         | 200，Markdown 文件内容                                      |

### 4.1 登录并创建文档

`POST /api/v1/auth/login`

```json
{"username":"demo_a","password":"<演示账号密码>"}
```

200 响应，`expiresIn` 的单位为秒。

```json
{"accessToken":"<访问令牌>","expiresIn":1800}
```

`POST /api/v1/documents` 的请求和 201 响应如下。

```json
{"title":"差旅报销制度"}
```

```json
{"documentId":"doc_101","title":"差旅报销制度"}
```

### 4.2 上传两个版本

`POST /api/v1/documents/doc_101/versions` 使用 `multipart/form-data`。先提交 `file=expense-v1.md`、`label=V1`，再提交 `file=expense-v2.md`、`label=V2`。每次上传生成新的版本编号。服务端校验文件格式、大小及文档权限。

第一次上传的 201 响应如下。后续示例假设第二次上传返回 `ver_202`。

```json
{"versionId":"ver_201","documentId":"doc_101","label":"V1","fileName":"expense-v1.md"}
```

### 4.3 创建任务并查询状态

`POST /api/v1/comparisons`，例如带请求头 `Idempotency-Key: expense-demo-001`。

```json
{"baseVersionId":"ver_201","targetVersionId":"ver_202"}
```

202 响应如下。

```json
{"taskId":"cmp_301","status":"QUEUED","statusUrl":"/api/v1/comparisons/cmp_301"}
```

两个版本必须属于同一文档、各自可读且编号不同。相同用户用同一幂等键重发相同请求时，服务端返回原创建响应。用同一键提交不同版本组合时返回 409。

轮询 `GET /api/v1/comparisons/cmp_301`。任务成功时的 200 响应如下。

```json
{
  "taskId":"cmp_301",
  "status":"SUCCEEDED",
  "stage":"EXPORTING",
  "reportId":"rpt_401",
  "error":null,
  "canRetry":false
}
```

状态包括 `QUEUED`、`RUNNING`、`WAITING_RETRY`、`SUCCEEDED` 和 `FAILED`。阶段包括 `PARSING`、`ALIGNING`、`ANALYZING`、`VERIFYING` 和 `EXPORTING`，尚未开始时为 `null`。未成功时 `reportId` 为 `null`。失败时 `error` 提供 `code` 与 `message`。查询到失败的任务仍返回 200，因为查询本身成功。

### 4.4 重试失败任务

当任务为 `FAILED` 且 `canRetry=true` 时，调用 `POST /api/v1/comparisons/cmp_301/retry`。服务端在同一任务下重新排队并保留历史执行记录。原子更新状态，避免并发重试排入多次。不允许重试时返回 409。

```json
{"taskId":"cmp_301","status":"QUEUED"}
```

### 4.5 查看并下载报告

`GET /api/v1/reports/rpt_401` 返回 200。下例只展示报告中的一条变化。

```json
{
  "reportId":"rpt_401",
  "taskId":"cmp_301",
  "baseVersionId":"ver_201",
  "targetVersionId":"ver_202",
  "items":[
    {
      "type":"MODIFIED",
      "summary":"报销申请期限由10个工作日缩短为5个工作日。",
      "inference":null,
      "evidence":[
        {
          "versionId":"ver_201",
          "blockId":"V1-P003",
          "location":{"lineStart":11,"lineEnd":11},
          "quote":"出差人员应在返程后10个工作日内提交报销申请。"
        },
        {
          "versionId":"ver_202",
          "blockId":"V2-P004",
          "location":{"lineStart":13,"lineEnd":13},
          "quote":"出差人员应在返程后5个工作日内提交报销申请。"
        }
      ]
    }
  ]
}
```

条目类型为 `ADDED`、`DELETED`、`MODIFIED`、`MOVED`、`NEEDS_REVIEW`。`inference` 为单独的分析文本，没有推断时为 `null`。证据用 `versionId` 与 `blockId` 联合定位。文本报告使用从 1 开始的行号，PDF 证据使用从 1 开始的 `location.page`。

`GET /api/v1/reports/rpt_401/download` 返回原始文件内容，响应头示例如下。

```http
Content-Type: text/markdown; charset=utf-8
Content-Disposition: attachment; filename="report-rpt_401.md"
```

查看和下载报告都检查对两个来源版本的访问权。下载接口根据报告编号查找文件，客户端只传报告编号。

### 4.6 错误约定

错误响应统一为 JSON，例如 `{"code":"VERSION_PAIR_INVALID","message":"请选择同一份文档的两个不同版本。"}`。

| 状态码 | 使用场景                                                 |
| ------ | -------------------------------------------------------- |
| 400    | 参数缺失、版本组合无效                                   |
| 401    | 登录失败，或访问令牌缺失、无效、过期                     |
| 404    | 资源不存在或当前用户无权访问该资源，避免暴露资源是否存在 |
| 409    | 幂等键冲突，或当前状态不允许重试                         |
| 413    | 文件超出大小限制                                         |
| 415    | 文件格式不支持                                           |

Java 负责内部 Worker 接口的鉴权和执行权检查。可靠任务阶段再定义领取、心跳、成功提交和失败上报的字段。接受结果前须校验任务编号和当前执行编号，避免过期执行覆盖新结果。

## 5. 首次验收

1. 运行本地对比，使用项目现有的两份样本，按人工答案核对 10 处变化和原文定位。
2. Web 版接通后，在 Apifox 按顺序登录、建文档、上传两个版本、创建任务、查看状态、读取报告、下载文件。
3. 用另一个账号复用已有编号，核对文档、任务、报告和下载均无法越权访问。
4. 在可靠任务阶段模拟一次可重试故障和一次执行进程中断，检查任务恢复且只产生一份有效报告。
