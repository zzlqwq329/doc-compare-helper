# Task 3 学习笔记 · 识别修改、新增、删除和待核对

对应代码是 [compare.py](../project/compare.py)，练习要求见 [Task 3](../docs/03-third-task.md)。这一项接着处理 [Task 2](task2.md) 第一轮配对剩下的段落。

## 函数做什么

| 函数 | 我的理解 |
| --- | --- |
| `group_by_text(blocks)` | 接收一版的段落列表，用原文当字典的键，值是包含这句原文的完整段落记录列表。Task 3 用这两份字典检查对方版本里有没有相同的原文。 |
| `unique_best_candidate(candidates)` | 接收一条段落的候选列表，每个候选是 `(对方段落编号, 分数)`。最高分只有一个时返回它的编号。候选为空或最高分并列时返回 `None`。 |
| `compare_versions(v1_blocks, v2_blocks)` | 接收两版的完整段落列表。先找未变和移动，再给剩余段落找修改候选，最后判定新增、删除和待核对。返回 `items` 列表，每项有 `type`、`old`、`new`。 |
| `main()` | 读取两份段落 JSON，交给 `compare_versions()`，再把返回的列表包装成 `{"items": items}`，写入 UTF-8 文件 `outputs/comparison.json`。 |

## 最重要的是读懂 `compare_versions()` 的顺序

1. **先配原文完全相同的段落。** 两版各出现一次才配对，同章记「未变」，跨章记「移动」。先处理这两类，剩下的段落再进入下一步。
2. **给符合条件的剩余段落打分。** 只比较同章、原文不同的段落。两版都有同一句原文且至少一版有多条时，相关的未配对段落留给「待核对」，跳过打分。`SequenceMatcher` 把原文的相似程度算成 0 到 1 的分数。达到 `0.60` 就把这对候选按旧编号、新编号各记一份，方便从任一端查找。
3. **双方都把对方选为唯一第一名，才算修改。** 例如 `V1-P003` 选中 `V2-P004`，`V2-P004` 反查也只选中 `V1-P003`，就确认这一对，把两端编号加入已配对集合。
4. **给仍未配对的段落分类。** 因原文重复配不上，或最初有达标候选却因并列、竞争配不上，都记「待核对」。其余旧段落记「删除」，其余新段落记「新增」。这里查的是最初记下的候选，候选已和别的段落配对时，原来的竞争记录仍然有用。
5. **把结果装进 `items`。** 配对结果保存两端的完整记录。删除只填 `old`，新增只填 `new`，每条待核对只填它所在的那一端。空的一端用 Python 的 `None`，写进 JSON 就是 `null`。每个输入段落在输出里出现一次，便于按原文和行号核对。

## 我卡过的地方

- **以为原文已经进了分组字典，就能配上。** 分组只是收集记录。比如一句话在 V1 出现两次、V2 出现一次，两版都能找到这句原文，但程序无法确定用哪个旧编号，三条都留待核对。
- **分不清候选字典的键和值。** `candidates_by_old["V1-P003"]` 取出一个列表，里面的候选像 `("V2-P004", score)`。反方向用 `candidates_by_new["V2-P004"]`，列表里的候选就像 `("V1-P003", score)`。一个元组里有编号和分数两个值，列表的长度才表示有几个候选。
- **看到 `0.93`，以为代码也用两位小数来选。** `:.2f` 仅影响打印。判断是否达到 `0.60`、是否并列，都是用原始分数。
- **反向查找时差点比错编号。** 新版反查得到的是旧版编号，所以要和 `old_id` 比。任一方向没有唯一第一名，或新版选中了另一个旧编号，这对就跳过。
- **以为修改结果直接存候选编号就够了。** `modified_pairs` 暂存两个编号。组装 `items` 时，`old_by_id` 和 `new_by_id` 用编号找回完整记录，所以还能看到 `V1-P003` 的「10个工作日」和 `V2-P004` 的「5个工作日」。

样本结果是 **5 对未变、1 对移动、6 对修改、1 段删除、2 段新增、0 段待核对**。这一版的阈值是 `0.60`，练习时改成 `0.70`，约 `0.64` 的 `V1-P006 → V2-P007` 就不会配成修改。

## 测试笔记

### 我怎么设计一条能抓错的测试

**先说出担心的错，再挑一组能让正确写法和错误写法给出不同答案的输入。** 比如，担心函数总选名单第一项，就把最高分放在第二项。用 `assert` 写出独立算出的预期结果，最后故意让程序犯一次这个错，确认同一个检查会失败。复习时，我要说清这条测试防什么错、失败时哪项结果不对，以及哪些情况它还检查不到。

### `test_compare.py` 用两份原文核对人工答案

[`test_比对结果与人工标注答案一致()`](../project/test_compare.py) 用 [V1 样本（13 段）](../samples/expense-v1.md)和 [V2 样本（14 段）](../samples/expense-v2.md)检查 [10 条人工标注](../fixtures/expected-changes.json)，包括 6 条修改、2 条新增、1 条删除和 1 条移动。它防漏报，也防程序多报变化。

- `build_items()` 从两份 Markdown 读出正文并调用比对，拿到程序这次算出的 `items`。`load_expected_changes()` 从人工标注文件读取预先写好的 `expected`。
- `make_key()` 把两边的每条变化整理成「变化类型、旧段落编号、新段落编号」，缺少一端就写「无」。比如报销期限从 10 个工作日改成 5 个工作日，对应 `('modified', 'V1-P003', 'V2-P004')`。
- **漏报看 `missing`。** 人工有这条，程序少了它。实验里，从本次运行的程序结果中划掉报销期限这条修改，它就出现在 `missing`，而断言要求 `missing` 为空。
- **误报看 `extra`。** 程序报了这条，人工答案里没有。实验里保留正确的「修改」，再给同一对段落加一条「移动」，pytest 确实报出 `('moved', 'V1-P003', 'V2-P004')`。人工答案只记录变化，所以找误报时会排除 `unchanged`（未变）。

### `test_units.py` 用专门设计的小输入检查规则

这个文件里的 8 条测试都检查 [`compare.py`](../project/compare.py) 的函数。`_make_block()` 是准备数据的辅助函数，用来构造带编号、章节和正文的段落记录。

| 测试函数 | 怎么设计输入，预期是什么 | 能抓住什么错 |
| --- | --- | --- |
| [`test_unique_best_candidate_returns_only_candidate()`](../project/test_units.py) | 名单只有 `V2-P001`，分数 `0.75`。应返回编号 `"V2-P001"`。 | 函数明明有一个候选，却返回表示谁都没选的 `None`。实验确认，总选第一项的错误仍能通过这条，所以要有下一条。 |
| `test_unique_best_candidate_selects_highest_score()` | 三项按 `0.70、0.90、0.80` 排列。最高分刻意放第二，应返回 `"V2-P002"`。 | 函数总选第一项，结果拿了 `0.70`，漏掉最高分。 |
| `test_unique_best_candidate_rejects_tied_highest_scores()` | 两项都拿到最高分 `0.90`，应返回 `None`。我自己把上一组的第一项从 `0.70` 改成 `0.90`，也构造出了并列。 | 函数在并列第一时擅自选中一个候选。用我设计的名单实跑，故意选第一项时断言失败。 |
| `test_unique_best_candidate_returns_none_for_empty_input()` | 传入空列表 `[]`，应返回 `None`。 | 程序收到空名单还直接找最大值。临时去掉 `max()` 的空输入处理后，调用函数时就报错了。 |
| `test_group_by_text_preserves_blocks_with_the_same_text()` | 三条不同编号的段落，第一和第三段正文相同，第二段正文不同。相同的两段应归到一组，另一段单独一组。我也用过「啊啊啊、啊啊啊、啦啦啦」设计同类例子。 | 后放进组的段落覆盖前一段。临时改成每组只保留最后一段后，检查发现第一段丢了。 |
| `test_group_by_text_returns_empty_groups_for_empty_input()` | 传入 `[]`，应返回空字典 `{}`，也就是一个组都没有。 | 没有正文却凭空产生一组。实验里让函数返回 `{'': []}`，测试就失败了。 |
| `test_compare_versions_requires_reciprocal_best_candidate()` | 让同一章的两条旧段落 A、C 都够资格选新版 B。A 和 B 约 `0.79`，C 和 B 约 `0.86`。C 选 B，B 也选 C，所以「修改」清单应只有 C → B。 | 程序只从旧版往新版选，漏掉反向检查。同一次临时运行里去掉反向检查后，B 同时被分给了 A 和 C，测试失败。 |
| `test_compare_versions_marks_all_tied_candidates_for_review()` | 旧版只有「10 个工作日」一段，新版同一章放两条内容都是「5 个工作日」的候选，编号各不相同。两对分数均约 `0.93`，三条段落应各有一条 `needs_review`（待核对）记录。 | 并列时擅自配成修改，或把有候选的旧段判为删除、新段判为新增。三种错误分别在临时运行中试过，测试都失败了。 |

### `test_guard.py` 检查调高门槛是否真的生效

[`test_higher_similarity_threshold_loses_annotated_modifications()`](../project/test_guard.py) 要防的是筛选时把门槛写死。它先用原门槛计算漏掉了哪些人工标注的修改，再用 `monkeypatch`（pytest 提供的临时替换功能，测试结束会恢复原设置）把门槛设到 `0.95`。断言要求原有漏报都还在，而且至少新漏掉一条修改。

我选过 `0.70` 做同类实验。初审人变化 `V1-P006 → V2-P007` 约为 `0.64`，在 `0.60` 时能配对，提高到 `0.70` 后成了漏报。另一次临时运行让筛选始终用 `0.60`，即使测试设成 `0.95`，两份漏报清单仍都是空的，所以测试失败。
